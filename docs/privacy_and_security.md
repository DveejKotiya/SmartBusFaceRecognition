# Privacy, Security, and Biometric Data Protection Guidelines

**Project:** AI-Based Face Recognition and Smart Bus Pass Verification System  
**Stage:** Stage 9 — Anti-Spoofing / Liveness Detection & Security Hardening  
**Scope:** College Engineering Prototype System  
**Status:** Updated for Biometric Liveness Verification and Edge Defense  

---

## 1. Executive Summary

The **AI-Based Face Recognition and Smart Bus Pass Verification System** operates on biometric data (facial imagery, 5-point facial landmarks, and 512-dimensional embedding representations) alongside personal educational records (roll numbers, departments, routes, and pass validity dates). 

Because facial biometrics are sensitive, personal, and unchangeable identifiers, this project adheres to **Privacy by Design** and **Data Minimization** principles tailored for a secure educational environment.

---

## 2. Core Privacy Principles

### 2.1 Complete Local / On-Device Processing
- All face detection (MTCNN), 5-point landmark extraction, liveness challenge-response verification, embedding generation (InceptionResnetV1), similarity comparison (cosine similarity), and pass business rules execute **100% locally** on the bus computer or campus server.
- **Zero Cloud Transmission**: Under no circumstances are student photos, video streams, facial landmarks, embeddings, or identity records transmitted over the internet or sent to third-party cloud APIs.

### 2.2 Strict Embedding & Biometric Vector Masking
- Face embeddings are 512-dimensional floating-point vectors generated by deep neural networks.
- **No Vector Exposure**: Raw 512-D float vectors are never displayed in the Streamlit UI, never printed in standard audit logs, and never exported in CSV reports.
- Embeddings are serialized in binary format (`models/embeddings.pkl`) accessible only to administrative filesystem accounts.
- The UI exposes only high-level biometric statuses (`READY`, `MISSING_IMAGES`, `MISSING_EMBEDDINGS`, `ERROR`) without leaking vector coefficients.

### 2.3 Ephemeral Landmark Processing & Zero Stream Retention
- **Volatile RAM-Only Landmarks**: The 5-point facial landmarks (`left_eye`, `right_eye`, `nose`, `mouth_left`, `mouth_right`) extracted by MTCNN for liveness tracking exist solely in volatile memory during the active session.
- **Zero Video / Landmark Storage**: Live camera frames, video clips, and intermediate landmark coordinate arrays are **never written to disk** or retained after processing.
- The liveness session state is cleared immediately once a boarding decision is reached or the session times out.

### 2.4 Sanitized Audit Logs & Reports
- Boarding event logs stored in SQLite (`entry_logs`) record strictly operational and audit metadata:
  - Timestamp
  - Student Roll Number & Name (or "UNKNOWN PERSON")
  - Bus ID & Route Code
  - Verification Decision (`APPROVED` / `REJECTED`)
  - Decision Reason Code (e.g., `PASS_VALID`, `LIVENESS_FAILED`, `LIVENESS_INCONCLUSIVE`, `PASS_EXPIRED`, `INVALID_ROUTE`, `COOLDOWN_ACTIVE`)
  - Scalar Cosine Similarity Score (e.g., `0.78`)
- **No Biometric Data in Logs**: Neither raw image pixels, facial coordinates, nor vector arrays are stored in the database or written to CSV exports.
- CSV report downloads are restricted to operational and audit fields only.

### 2.5 Controlled Local Storage & Directory Sanitization
- Enrollment photos are kept in `data/students/faces/<student_id>/`.
- Directory paths are strictly sanitized with path traversal protections (`Path(student_id).name` and `is_relative_to()` verification) to prevent arbitrary file access.
- In a production deployment, this directory must have restricted filesystem permissions (e.g., readable only by the bus terminal service daemon, `chmod 700`).
- Student images are not displayed publicly on external terminal displays. When previewed by administrators, the interface displays only enrollment counts unless explicitly inspected in an authenticated maintenance mode.

## 3. Student Consent & Ethical Guidelines

1. **Informed Consent**:
   - Enrollment in the facial bus-entry system is voluntary and conducted with student awareness.
   - Students must be informed that their photograph is used exclusively to generate an on-bus verification model for campus transit.

2. **Dignity & Accessibility in Liveness Checks**:
   - The active challenge-response mechanism provides clear, polite on-screen visual prompts (e.g., "TURN HEAD LEFT", "TURN HEAD RIGHT") with high-contrast color indicators.
   - Liveness challenges are non-punitive: failing a liveness check does not imply disciplinary wrongdoing or fraud; it merely indicates that the automated vision sensor could not confirm a live 3D subject.
   - Accommodations are provided for students with physical disabilities, neck mobility limitations, or visual impairments via the manual fallback protocol.

3. **Purpose Limitation**:
   - Biometric embeddings and liveness checks generated for the Smart Bus system are strictly forbidden from being used for tracking outside the bus transit perimeter, surveillance, or grading purposes.

4. **Data Deletion & Right to Erasure**:
   - When a student graduates, discontinues the bus service, or revokes consent:
     1. Their image directory in `data/students/faces/<student_id>/` is permanently purged.
     2. Their record is removed from `models/embeddings.pkl` via `EmbeddingStore.remove(student_id)`.
     3. Their database record in `students` and `bus_passes` is marked as `REVOKED` or archived in compliance with college record retention rules.

## 4. Manual Fallback & Anti-Discrimination

Automated facial biometric and liveness systems can encounter false rejections due to extreme lighting, eyeglasses, religious headwear/face coverings, medical face masks, camera hardware failures, or physical mobility constraints.

- **Manual Fallback is Mandatory**:
  - If a student's face is unrecognized (`UNKNOWN_PERSON`), or if liveness returns `LIVENESS_FAILED` / `LIVENESS_INCONCLUSIVE`, the student is **never stranded, penalized, or denied transit arbitrarily**.
  - The bus conductor or driver follows the established manual fallback procedure:
    1. Inspect the student's physical College ID Card.
    2. Check the student's roll number in the admin dashboard search interface (`src/ui/students_page.py`).
    3. Verify active pass validity and route eligibility.
    4. Manually authorize boarding.
  - The manual boarding event can be recorded in the system audit logs.

## 5. Security Measures for Prototype Deployment

| Vulnerability Vector | Prototype Mitigation | Production Recommendation |
| :--- | :--- | :--- |
| **Physical Storage Theft** | Local database & `.pkl` stored in application root; git-ignored. | Full-disk encryption (BitLocker / LUKS) with TPM-sealed keys on on-bus hardware. |
| **SQL Injection** | 100% parameterized SQL queries (`?` placeholders) across all database modules. | Role-based database users with least privilege and read-only views for terminals. |
| **Unauthorized UI Access** | Single-user local admin interface running on `localhost:8501`. | Multi-factor authentication, TLS/HTTPS, and role-based access control (Admin vs. Conductor). |
| **Biometric Tampering** | Pickled embeddings with strict deserialization checks; path traversal guards. | Cryptographic signing of embedding bundles via TPM / hardware keystore (HMAC-SHA256). |
| **Replay / Spoofing (Photos & Screens)** | Active challenge-response (head yaw ratio) + landmark motion variance tracking (`src/vision/liveness.py`). | Multi-spectral near-infrared (NIR) / depth cameras (e.g., Intel RealSense) for 3D liveness. |
| **Double-Boarding / Pass Sharing** | 5-minute database-backed boarding cooldown enforced by `PassVerifier`. | GPS-geofenced trip completion checks and cross-bus sync. |
| **Data Leakage in Exports** | CSV export queries project only 9 operational columns, excluding all biometric vectors. | Automated audit log hashing and immutable append-only storage. |

## 6. Version Control Hygiene & Secure Backup Procedures

### 6.1 Files Strictly Excluded from Git (`.gitignore`)
The following files process personal identifiable information (PII) or biometric data and **must never be committed to public or shared version control repositories**:
- `data/students/faces/**`: Raw facial photographs of enrolled college students.
- `models/embeddings.pkl`: Serialized 512-dimensional biometric feature embeddings.
- `data/smart_bus.db` & `*.db-wal`: Production SQLite database containing student profiles, pass validity records, and entry event history.
- `exports/*.csv`: Exported boarding audit logs containing timestamps, names, and roll numbers.
- `logs/` and `scratch/`: Local execution logs and developer scratch dumps.

### 6.2 Data Backup & Disaster Recovery Protocol
Because biometric data is excluded from version control, the system requires a secure offline backup protocol:
1. **Database Hot Backup:** Use SQLite's online vacuum/backup command:
   ```bash
   sqlite3 data/smart_bus.db ".backup 'secure_backup/smart_bus_backup.db'"
   ```
2. **Master Student CSV Backup:** Store `data/students/students.csv` on an access-controlled campus server.
3. **Face Image Archive:** Store enrollment photos in an encrypted tarball (`gpg --symmetric student_faces.tar.gz`) on offline storage.
4. **Reproducibility:** If `models/embeddings.pkl` is ever corrupted or lost, it can be regenerated at any time by executing `src/vision/build_student_embeddings.py` against the backed-up face images.

## 7. Academic Scope & Limitations


This implementation is an **educational engineering prototype**, not a commercial biometric authentication appliance.
- The active yaw challenge reliably catches passive 2D presentation attacks (printed photographs and static phone screen displays).
- However, advanced spoofing attacks (such as interactive deepfakes, custom 3D silicone masks, or synchronized video playback) may present vulnerabilities.
- True production systems should combine active behavioral challenges with specialized hardware (structured light sensors, thermal cameras, or active near-infrared illumination).

## 7. Regulatory Reference

This policy draws upon global standards for student data privacy and biometric processing:
- **Principle of Lawfulness, Fairness, and Transparency**: Inform students of automated processing and provide human-in-the-loop fallback.
- **Principle of Data Minimization**: Collect only images and compute only the minimum landmarks/embeddings necessary for boarding verification.
- **Principle of Storage Limitation**: Retain active embeddings only for currently enrolled bus pass holders; discard video frames and landmarks immediately from RAM.
- **Principle of Integrity and Confidentiality**: Prevent unauthorized access, tampering, or extraction of biometric data templates.
